fix(mobile): prevent photo-upload crashes & hangs on bad connections

Users in Cuba (poor connectivity) report the app crashing and going
back ("se bloquea y regresa atrás") when adding a selfie, vehicle photo,
or document. Sentry has no matching image/upload issue in 90d — the
fingerprint of a native OOM that the OS kills before the crash envelope
can upload. Two independent, code-confirmed failure modes are fixed here
(all JS, no native module change; no migration / Edge Function change):

1. Upload hangs on a flaky link. uploadFileFromUri (the canonical helper
   every photo upload routes through) had no timeout or retry, so
   functions.invoke('storage-upload') could hang forever → infinite
   spinner perceived as a freeze. Race each attempt against a 45s
   timeout and auto-retry once on a timeout/network-class failure; a
   real EF denial ({ error } body) is never retried. Rebuild FormData
   per attempt (a body is single-use). +4 vitest cases (10/10 pass).

2. Native OOM decoding full-res bitmaps. Every flow runs
   ImageManipulator on the source; on Android it decodes the full
   ARGB bitmap (48–430 MB for a 12–108 MP photo) → OS kill on low-RAM
   devices, uncatchable from JS. Worst path is the avatar: it picked at
   quality:1 and fed the full-res image to AvatarCropModal, which both
   renders it full-res AND crop-manipulates it (double memory), and it
   never pre-compressed. New shared resizeImageForCrop() downscales to
   ≤1600px before the crop modal (returning resized dims so crop
   geometry stays correct); wired into all three avatar screens + picker
   quality lowered to 0.8. Dispute evidence now compresses sequentially
   instead of Promise.all (up to 4 concurrent full-res decodes).

Ships in the next store build (or OTA if #816 lands).
