fix(fx): the FX watchdog was red on a healthy system

sync-exchange-rate answered 502 for any unsuccessful run, so an elToque
rate-limit on one attempt looked exactly like a genuine FX outage. Over 6h
of production runs: 6 of 24 succeeded, every failure [429,429] + the dead
403 scraper. That still keeps the rate ~1h fresh against a 24h requirement,
yet cron_http_health_status sat permanently 'failing' while fx_health_status
said 'ok' -- the two watchdogs contradicting each other.

The status code now reports the invariant (is the stored rate still good?)
rather than the luck of one upstream request: 200 refreshed:false while the
rate is below fx_stale_alert_hours, 502 once it is not. Config faults stay
loud regardless of freshness. Not a cron_http_expectations row -- accepting
502 for this job would silence the real outage too.

Also, measured from the same 24 runs, the 1.5s retry recovered 1 of 18
failures, so the ladder was spending budget for ~6%. Widened the spacing,
added pre-flight jitter to step off the :00 cron boundary, and fenced the
whole thing with a wall-clock deadline: cron_http_post allows 30000ms, past
which pg_net records NULL and the diagnostic body is lost. jitter_ms and the
spacing ride along in the response so the hypothesis is measurable, not
assumed.

Fixes the FX kill switch while here: platform_config.value is jsonb and
exchange_rate_auto_update is a boolean in production, but the check was
`=== 'false'`, which a boolean can never satisfy -- turning the sync off did
nothing. auto-admin, directions-google and create-stripe-payment-intent all
already guard both shapes.
